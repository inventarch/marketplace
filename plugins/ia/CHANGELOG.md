# Changelog

## 1.7.0

Run the method reports as advisory hooks for the method kit; Kit post hooks see the person's answers; Re-cut the method kit 0.8.0 with declared activation; The method gate checks that the CLI admits the workspace.

- **Run the method reports as advisory hooks for the method kit.** The bundled inventarch/ia-method-kit is now 0.9.0, and the public kits package is 1.0.6. The kit ships onwrite.json and handlers.json, which run one new script of the core, scripts/method-advise.mjs, after a write to a .ia record, after a Bash or PowerShell call and at a resumed or compacted session. It reports the ceiling and the exit evidence of the tasks in the changed or uncommitted records (at most 2 from a written file, 3 per call), says how many tasks it evaluated and how many it did not, prints anything it could not evaluate as not evaluated and never as clear, never downloads a CLI, and blocks nothing. It is not a complete check: the full report, scripts/method-gate.mjs, is. A handlers.json run may now be exactly ${PLUGIN}/scripts/method-advise.mjs, an allowlist of that one script, accepted on session and tool post handlers only, run only for a trusted kit inside an IA workspace. The ia-method contract is 0.2.0 with REQ-METHOD-02, the exit evidence of closed tasks. A core older than this release skips the kit's handlers.json with a reason, and its onwrite.json command finds no script and reports nothing; upgrade the plugin with the kit. The method gate script is unchanged; ceiling.mjs now honours IA_CORE_METHOD_READ_TIMEOUT_MS as exit-evidence.mjs does.
- **Kit post hooks see the person's answers.** The ia plugin's PostToolUse hook now also runs for AskUserQuestion, so a kit's post handler that declares AskUserQuestion receives the question and its answers. ia-governance uses this to witness a plan approval or a change acceptance the person gives through a question; before, those answers never reached it, and a ledger whose only cure was the person's acceptance could not be sealed. AskUserQuestion reaches post handlers only: no kit can block or rewrite a question. This widens the qualified hook set for review (decision public-kit-handlers).
- **Re-cut the method kit 0.8.0 with declared activation.** The bundled inventarch/ia-method-kit is now 0.8.0, and the public kits package is 1.0.5. Eleven governance rules declare when they apply, by phase, primitive or move; the two blocking rules stay universal. The lines are declarations: the resolvers do not yet put move, artifact-set or word into the coordinate, so they narrow no delivery today. The kit README adds the activation table, the authoring contract rows as declared and not evaluated, and the open items. Releases up to 0.7.3 are unchanged.
- **The method gate checks that the CLI admits the workspace.** method-gate.mjs asks the CLI to validate the workspace before it runs the reports, and evaluates only a workspace reported as admitted. A refused workspace, any other status, or a validate that cannot run leaves both rules not evaluated and names the error codes, and the JSON carries admission. A child's printed time limit is at least one second. The README says this catalogue's own CI runs the gate as a report, and that a repository that ignores its lock restores it first.

## 1.6.0

Add the exit-evidence report and a report-only method gate.

- **Add the exit-evidence report and a report-only method gate.** Two new scripts read a repository's work records and only report. exit-evidence.mjs lists each closed task as evidenced, exempt, refused, inconclusive, stale, no evidence or unknown, from the observation records that name it. method-gate.mjs runs it with the ceiling report and says how many of its two rules were evaluated. Neither blocks: they exit 0 for findings, so read the position that starts each line. The ia:work skill says how to record evidence in the right order; the README shows the gate in CI.

## 1.5.0

Move to IA 3.6.0.

- **Move to IA 3.6.0.** The IA door is now `@inventarch/mcp-door` 3.6.0, and it refuses a kit the repository binds but its `.ia/distributions.lock.json` does not install; the remedy is `node <ia plugin>/scripts/kit.mjs bind <kit> --install --apply`, or `kit.mjs add` for a kit `@inventarch/public-kits` does not carry. In a repository that pins `@inventarch/cli`, `kit.mjs add` and `bind --install` need that pin to be 3.6.0. Every IA CLI the plugin starts gets `IA_NO_HANDOFF=1`, so the CLI the plugin chose is the CLI that runs, and from an installed `@inventarch/cli` the plugin runs the CLI's own `main` entry (`dist/main.js`) rather than 3.6.0's hand-off launcher. With no consumer workspace named, the closure path follows IA's repository default, except for a distribution this repository authors with packaged workspace roots, where the default must be one of them. The bundled kits are re-cut on CLI 3.6.0: `ia-method` 0.7.3, `ia-kb` 0.9.4 and `ia-authoring` 0.1.4, carried by `@inventarch/public-kits` 1.0.4.

## 1.4.0

Bind installs the kits it binds; Bound execution requires an installed kit; Install your bound kits before the IA 3.6.0 release; Retain workflow metadata in installed kit archives; The session bootstrap no longer routes every request through a lane.

- **Bind installs the kits it binds.** kit.mjs bind now refuses a kit the repository lock does not install, on a preview too and with --key, and writes nothing; --install installs it first. For the kits `@inventarch/public-kits` carries, --install runs `ia install --package @inventarch/public-kits@<version> --apply --yes` (a workspace with no lock gets a language-only lock and a restore first), which needs npm and the registry; any other kit installs as kit.mjs add does. The refusal names the remedy for the kit: the package route for the kits the package carries, kit.mjs add for the rest. The session start names every bound kit the lock does not install. The bundled kits' guidance now teaches `kit.mjs bind <kit> --install --apply` as the way to install and bind a kit, and says a bound kit the lock does not install is refused with `IA-CORE-KIT-NOT-INSTALLED`: the `ia-authoring` `convention` and `playbook`, the `ia-authoring-record` installed-kits `convention`, the `ia-kb` `IA-CORE-NO-METHOD` remedy and `case` records, and the `ia-method` README.
- **Bound execution requires an installed kit.** resolve.mjs and check.mjs now refuse a kit the repository binds but its own lock does not install, with IA-CORE-KIT-NOT-INSTALLED, before anything is retained, restored, written or run. This holds for the ordinary and the qualified routes (--qualified, --qualified-input), and a copy the plugin carries, the IA home holds or a task pin retained never stands in for the lock. A kit row of an npm package carrier in the lock's entries counts as installed, as it does for the IA runtime; a pin older than the installed version keeps running from its retained bytes. The refusal also carries the kit's canonical id as `error.kit`, and a binding written with a kit's folder name (such as `ia-authoring`) is guarded as the kit it names. --kit with no binding and the unbound resolve outside a workspace are unchanged.
- **Install your bound kits before the IA 3.6.0 release.** The next release of the `ia` plugin moves to IA 3.6.0, whose door runs a kit the repository binds only when the repository's own `.ia/distributions.lock.json` installs it. Run `kit.mjs bind <kit> --install --apply` now for each kit you bind (the session start names any that are missing); a repository that installs on this release keeps working at the next. The bundled `ia-authoring` 0.1.3 and `ia-kb` 0.9.3 are patch re-cuts whose guidance teaches that route; `ia-method` stays at 0.7.2, because its archive is unchanged and only its README text changed.
- **Retain workflow metadata in installed kit archives.** Public kit archives now include binding recommendations, full-procedure delivery settings and check metadata so CLI-only setup can discover and use the same workflows as the plugin.
- **The session bootstrap no longer routes every request through a lane.** The SessionStart context says reading, building, testing, editing and submitting a change need no binding, plugin, door or private access, routes through the lanes only when a task needs a method, and refuses only the operation that needs one. It carries a one-line ia-bootstrap marker and a sentence naming what needs a bound method or private authority, both kept however long the bindings, the notices or the plugin path are (the whole context stays within 2,500 characters), and names a locked kit the plugin does not carry.

## 1.3.0

Bundle the InventArch account connector.

- **Bundle the InventArch account connector.** The core now ships the InventArch account connector (MCP server inventarch, with the public Claude Code OAuth client), so signing in through /mcp is enough: ia:init then lists the kits the account offers, downloads each through its signed URL, verifies the SHA-256, installs it with kit.mjs add --from and binds it as the kit recommends. The session-start account offer is now a one-line pointer to that sign-in. Also fixes kit.mjs add --from on an archive whose absolute path has a drive letter under GNU tar.

## 1.1.0

The lanes go through the IA door, kits run handlers and depend on other kits, only trusted kits run code, and governance arrives as a kit (decisions `public-door-mcp`, `public-kit-handlers`, `public-kit-trust`, `public-kit-dependencies`, `public-delegate`, `public-governance-probe` and `public-core-hooks`). ia-kb 0.9.0, not yet published, is re-recorded from 57ebf44 with the knowledge-repository layout of the operator's ruling dec-132 (one `.ia/src`; one `@workspace` for a personal or single-team KB; for an organisation store one `@workspace` per department plus an organisation `@workspace` that also declares the root; `workspaces/<name>/` only for a workspace released or adopted on its own); ia-method 0.7.0 and ia-authoring 0.1.0 stand.

- The plugin ships the IA door as its MCP server `ia` (`.mcp.json`: `node scripts/door.mjs`, a launcher that starts `npx -y @inventarch/mcp-door@3.4.1` never through a shell (on Windows, where `npx` is a `.cmd` shim, it runs npm's `npx-cli.js` with `node`), with stdio passed through and `IA_KITS_DIR` set to the bundled kits). Claude Code names its tools `mcp__plugin_ia_ia__<tool>`. Codex reads a plugin's `.mcp.json` too, so the Codex manifest keeps the door off with `"mcpServers": {}` until it is qualified there.
- The lanes call `ia_session` once per session, then `ia_catalogue {lane}` to choose a key and `ia_method {key}` for the packet. Until `@inventarch/mcp-door` ships `ia_method`, they fall back to `scripts/resolve.mjs` and `kit.mjs list`.
- The reader, checker and worker allowlists name the door's tools by their plugin-scoped names; the checker now has the door tools too. The old `mcp__ia-workspace` entries never matched a plugin server and are gone.
- The SessionStart bootstrap also runs on `compact`, and then re-injects the current task pin's summary and how to resolve the same method again.
- Kit handlers: a kit's `handlers.json` declares session, prompt, tool (pre or post, with a tool-name match) and stop handlers, and `scripts/handlers.mjs` runs them from SessionStart (every source), UserPromptSubmit, PreToolUse, PostToolUse and Stop. Only installed kits whose folder holds the script run; each kit's context is capped at 2,000 characters; a pre block is honoured only with `.ia/governance.json`; with no handler declared every hook is a silent no-op. `onwrite.json` runs as tool post handlers, from the kits in `<IA home>/kits` too. `handlers.json` is a sidecar the sources digest covers, and `kit.mjs check` refuses a handler script that is not a declared asset.
- Kit trust (decision `public-kit-trust`, `scripts/lib/trust.mjs`): a kit runs code through `handlers.json`, `onwrite.json` or `checks.json` only when its publisher, its id's namespace, is on `config/trusted-publishers.json` (`inventarch` alone; nothing extends it at run time, since an agent with a shell could approve itself) and its sources digest is its latest recorded release's; a handler's script must also be a declared asset. Any other kit is data only: a handler entry may carry a `context` text, delivered with no process run; its `run` entries and on-write commands are skipped, its checks refuse `IA-CORE-KIT-UNTRUSTED`, and SessionStart names each such kit once with why. A `pre` handler of a kit whose publisher is not on the list never blocks; a trusted one that fails in a governed repository still refuses the call, now also when it times out, answers past the output cap or is still running when the hook's budget ends. An altered gate fails closed: in a governed repository, while a kit whose id names a trusted publisher declares a `pre` handler the trust check refuses (its bytes are not its recorded release, or its script is not a declared asset), every pre-tool call is refused, and the reason and the session-start notice name the kit and the fix (reinstall it with `node <ia plugin>/scripts/kit.mjs add --from <release> --apply`, or remove `.ia/governance.json`). The governance notice names an installed governance kit that may not run, and `kit.mjs check` reports `runsCode` per kit. A retained task pin carries the trusted list too.
- Process hygiene, not a sandbox (`scripts/lib/hygiene.mjs`): every child the handler, on-write and check runners start gets an allowlisted environment (the command path, the OS and home folders, locale, git's configuration lookup, `CLAUDE_PID`, and `IA_*` without credential-like names; never `NODE_OPTIONS` or `NODE_PATH`), its process tree is killed on its deadline (a POSIX process group, or `taskkill /T` on Windows), and a handler or on-write child keeps at most 256 KiB of stdout and of stderr. The handler and on-write runners are asynchronous now, and their hook entry points wait for them.
- The governance probe no longer looks for a plugin: in a repository with `.ia/governance.json` where no installed kit declares governance handlers (a tool pre handler), it says "this repository is governed; add the ia-governance kit (`ia kit add`)".
- Kit dependencies: a kit whose `.ia/release.json` depends on another kit finds it carried by the plugin, in `<IA home>/kits` or next to it, and adoption (`kit.mjs add`), `add --from` and the restored read root vendor the dependency's recorded release with `ia install --catalog`. `add --from` installs a dependency it finds only next to the kit into `<IA home>/kits` alongside it, dependencies first (the result lists them under `alongside`), so the installed kit resolves it from the home.
- Release versions are strict semver everywhere the core reads or writes one: the release index (either format), each `releases/<version>.json`, which a row must name exactly, `.ia/release.json` and the `add --from` install target, which must stay inside `<IA home>/kits`. `add --from` refuses a kit folder that holds a link, and a handler runs only when its script, links followed, sits inside its kit.
- The user-invoked `ia:delegate` hands one packet-driven step to `codex exec` or `claude -p` with the door and the packet inline, one level deep (`IA_DELEGATION_DEPTH`), with a timeout. It is off until the person sets `"delegation": true` in `~/.ia/config.json`.

## 1.0.0

The first public release, cut on 2026-10-30 from InventArch's internal catalogue with fresh history (decisions `public-catalogue-cut` and `public-core-1-0-0`). It is a breaking release: repositories bound to a kit this core no longer carries must rebind.

- The plugin is `ia` (`ia@inventarch`; decision `public-plugin-ia`). Its model-invocable skills are the three lanes, `ia:work`, `ia:knowledge` and `ia:delivery`; the former router became the user-invoked `ia:init`, with the CLI-rendered plugin's init steps merged in, beside a new `ia:doctor`. Agents are `ia:reader`, `ia:checker` and `ia:worker`.
- Licence Apache-2.0; repository `inventarch/marketplace`.
- The bundled kits are exactly the public defaults: `ia-method` 0.7.0 (Work), `ia-kb` 0.9.0 (Knowledge) and `ia-authoring` 0.1.0 (Delivery; it replaces the retired `inventarch/host-authoring-kit` and `inventarch/catalogue-authoring-kit`). Each lane's entry capability is a whole four-phase procedure; Knowledge `place` maps to the plan phase; the core names no whole-procedure activity of its own.
- Kit lookup in two places: `config/kits`, then `<IA home>/kits/<kit>/<version>/`.
- `scripts/kit.mjs` user verbs: `list`, `add` (also `add --from <folder|archive>`), `bind`, `upgrade`, `repin`, `rebind` and `check`, each previewing unless `--apply` and validating before it writes; `root`, `status` and `adopt` stay.
- Releases format 2: the core reads a release index and `releases/<version>.json` (and still format 1); `lib/releases.mjs` converts losslessly; release history is left out of the implementation digest and the method closure capture.
- The SessionStart hook offers an InventArch account once per session at startup, never blocking, with no network and no token (suppressed by `"accountOffer": false` in `~/.ia/config.json`, `IA_NO_ACCOUNT_OFFER=1` or `CI`), and says once when a repository has `.ia/governance.json` but the governance plugin is not installed.
- Pins `@inventarch/cli` 3.4.1, with a regenerated qualified runtime cohort.
