# 🧭 ia · the InventArch core plugin

[![ia plugin](https://img.shields.io/badge/dynamic/json?url=https%3A%2F%2Fraw.githubusercontent.com%2Finventarch%2Fmarketplace%2Fmain%2Fplugins%2Fia%2F.claude-plugin%2Fplugin.json&query=%24.version&label=ia%20plugin)](CHANGELOG.md) [![IA CLI](https://img.shields.io/badge/%40inventarch%2Fcli-3.6.0-blue)](https://www.npmjs.com/package/@inventarch/cli) [![License](https://img.shields.io/badge/license-Apache--2.0-green)](https://github.com/inventarch/marketplace/blob/main/LICENSE)

The core plugin: it carries no method of its own. Three entry points, `work`, `knowledge` and `delivery` (`delivery` took `development`'s place), go through the IA door this plugin ships as its MCP server `ia` (`.mcp.json` runs `node scripts/door.mjs`, which starts `npx -y @inventarch/mcp-door@3.6.0`, never through a shell (on Windows it runs npm's `npx-cli.js` with `node`); decision `public-door-mcp`; `.mcp.json` also carries the account connector `inventarch`, decision `public-account-connector`): `ia_session` once per session, `ia_catalogue {lane}` to choose a key, and `ia_method {key}`, which reads which method kit the repository binds for that key, pins it to the task and delivers one packet; the agent follows only the packet. The public default kits ship under `config/kits/`: [`ia-method`](config/kits/ia-method/README.md) (Work: the IA operating loop, the provisional-foundation ceiling, and one method capability per public record word), [`ia-kb`](config/kits/ia-kb/README.md) (Knowledge: placement, document binding, upkeep, checks and review) and [`ia-authoring`](config/kits/ia-authoring/README.md) (Delivery: record, host and catalogue authoring). Further kits are looked up in `<IA home>/kits/<kit>/<version>/`, where `scripts/kit.mjs add --from` installs them (decision `public-kit-lookup`). Each lane's entry capability is a whole procedure, orient, plan, act and learn (decision `public-opal-per-lane`).

## What runs where

| Situation | What the core does |
| --- | --- |
| No `.ia/src` at or above the folder | The bootstrap says nothing about a workspace (at startup it may still make the account offer); a resolve refuses `IA-CORE-NO-WORKSPACE`. The skills say what is unconfigured. |
| Any workspace | The context never makes routing a precondition. It opens with "When a task needs a method, route it through the lanes", says reading, building, testing, editing and submitting a change need no binding, plugin, door or private access, and ends with a reserved tail that cannot be cut: one sentence (an operation that needs a bound method or private authority refuses alone, naming it; everything else continues), the one-line marker `ia-bootstrap v1 public-contribution=available needs-method=ia:work,ia:knowledge,ia:delivery needs-authority=declared-operations` (parse it with `^ia-bootstrap v1( [a-z-]+=\S+)+$`; unknown keys are ignored), and the resolve instruction, which applies when a method is needed and gives up its path before anything reserved is cut. The whole context, notices and a compaction's pin included, stays within 2,500 characters. A locked kit this plugin does not carry is named by itself, and so is every bound kit the lock does not install (one reserved line of at most about 400 characters that no truncation drops, with `kit.mjs bind <id> --install --apply`). |
| A workspace with no `.ia/bindings.json` | The bootstrap says nothing is bound; only an operation that needs a method refuses, as `IA-CORE-NO-METHOD`, and a resolve names `kit.mjs list` and the kits that recommend the key (`kit.mjs bind <kit> --install --apply` installs the kit when the lock does not and writes their keys). |
| Session startup | Once per session, never blocking: the pointer to sign in to the bundled InventArch connector (`/mcp`) when no InventArch account is found (suppressed by `"accountOffer": false` in `~/.ia/config.json`, `IA_NO_ACCOUNT_OFFER=1` or `CI`), and, in a repository with `.ia/governance.json` where no installed kit declares governance handlers, a notice that it is governed and to add the `ia-governance` kit (decisions `public-account-pointer`, `public-governance-probe`). |
| A compaction | The bootstrap runs again (`compact`) and re-injects the current task pin: the task, its revision, each pinned key's kit, version and capability, and how to resolve the same method again (`ia_method {key, task}`, or the resolver with `--project` and `--task`). |
| A kit declares handlers (`handlers.json`) | `scripts/handlers.mjs` runs them for the hook event, for installed kits whose folder holds the script (decision `public-kit-handlers`): each gets the hook JSON on stdin and `IA_KIT_ROOT`, `IA_WORKSPACE_ROOT` and `IA_HOME`; their `additionalContext` is merged, at most 2,000 characters per kit; a `pre` handler's block applies only with `.ia/governance.json`. With no handler declared, every hook is a silent no-op. |
| A kit that is not trusted to run code | Only a kit whose publisher is on `config/trusted-publishers.json` (`inventarch`) and whose bytes are its recorded release runs code (decision `public-kit-trust`, `scripts/lib/trust.mjs`). Any other kit is data only: a handler entry's `context` text is delivered with no process, its `run` entries and `onwrite.json` commands are skipped, its checks refuse `IA-CORE-KIT-UNTRUSTED`, and SessionStart names it once with why. Its `pre` handlers never block, unless its id names a trusted publisher: in a repository with `.ia/governance.json`, such a kit whose `pre` handler may not run (an altered gate: its bytes are not its release, or its script is not a declared asset) refuses every pre-tool call, naming the kit and the fix (reinstall it with `node <ia plugin>/scripts/kit.mjs add --from <release> --apply`, or remove `.ia/governance.json`). |
| Any child a kit runner starts | Hygiene, not a sandbox (`scripts/lib/hygiene.mjs`): an allowlisted environment (never `NODE_OPTIONS` or `NODE_PATH`, never a credential-like name), the process tree killed on its deadline, and a hook child's stdout and stderr capped at 256 KiB each. In a governed repository a trusted `pre` handler that fails, times out or answers past the cap refuses the call. The catalogue's `docs/hosts.md`, "Kit trust and process hygiene", lists the names and the limits. |
| A kit depends on another kit | Adoption, `add --from` and the restored read root find the dependency (carried, in `<IA home>/kits`, or next to the kit), check that its sources are its recorded release, and vendor it with `ia install --catalog` (decision `public-kit-dependencies`). `add --from` installs a dependency found only next to the kit into `<IA home>/kits` alongside it. |
| A bound activity, kit not installed | Refused with `IA-CORE-KIT-NOT-INSTALLED` (`kit <id> is bound by this repository but its lock does not install it; run kit.mjs bind <id> --install --apply (or ia install --package @inventarch/public-kits@<version> --apply --yes), then resolve again`, the remedy being the package route for a kit the public-kits package carries and `run kit.mjs add <id> --apply (or ia install <id>)` for any other, with the canonical id also as `error.kit`; a binding written with a kit's folder name is guarded as the kit it names) before anything is retained, restored, written or run: no retained closure, no pin, no child process. `resolve.mjs` (ordinary and `--qualified`) refuses right after the binding is chosen, `check.mjs` in every way it selects kits (a task pin, the bindings, `--kit` when the bindings or the pin bind that kit) and in `--qualified-input`. A copy the plugin carries, the IA home holds or a task pin retained never stands in for the lock. `--kit` with no binding, and `resolve.mjs --kit --capability` outside a workspace, need no lock row. |
| A bound activity, kit installed (`.ia/distributions.lock.json`: a `packages` row, or a kit row of a package carrier in `entries`) | Any row naming the kit counts, at any version: a task pin older than the installed version keeps running from its retained bytes. The method still comes from the restored kit; the laws and seat mandates come from the repository's own position at the seat (`--seat`). If the repository cannot position (an unrestored clone), the resolve refuses with IA's hint. |
| A task folder (`--project`/`--task`, or `IA_CORE_RUN_ROOT`) | The resolve is pinned: later resolves keep the pinned kit version and report `kitUpdateAvailable`; `--rebind` writes a new revision with `supersedes`. |

Delivery checks the optional hosted stage for UX, UI, design-system and brand intent. Only an operator-bound, authorized and available service executes remotely; missing binding or unavailable runtime continues through native Delivery resolution. The four offerings share one selected hosted workspace.

## Contracts

**Bindings** (`<repo>/.ia/bindings.json`, interim until lowered to records): `{ "format": 1, "bindings": { "<entry>.<activity>": { "kit", "capability" } }, "precedence": [kit ids], "defaults": { "<entry>": { "kit", "capability" } } }`. A key may hold a list of candidates; `<entry>.*` answers an entry's other activities; `precedence` (first wins) resolves several candidates for one key, else `IA-CORE-CONFLICT` lists them.

**Task binding** (`<IA home>/work-v1/<project>/<task>/binding.json`, the IA home being an absolute `IA_HOME`, else `~/.ia`; format 3): `{ format: 3, revision, workspace: {root, revision}, task, kits: { <kit id>: {version, archive, sources, implementation, retained} }, keys: { <entry>.<activity>: {kit, capability, profile, records, scopeKey, intent} }, createdAt, supersedes }`, one entry per activity key the task resolved and one version per kit. A new key joins in a new revision; a changed binding for a pinned key needs `--rebind` (`IA-CORE-REBIND-REQUIRED`). Earlier revisions stay as `binding.<n>.json`; formats 1/2 remain inspectable, but execution requires an explicit rebind to retained bytes. Compare-and-swap publication under a task lock refuses stale writers; an abandoned lock requires operator recovery. A pin for another repository is refused (`IA-CORE-RUN-MISMATCH`). **Unbound resolve**: outside an IA workspace, `--kit <kit> --capability <name> [--profile <name>]` names the method directly (`binding.via: "unbound"`, nothing pinned); inside one it is refused (`IA-CORE-UNBOUND-IN-WORKSPACE`).

**Packet**: `{ contract: 1, resolver, binding: {key, via, kit, capability, revision, supersedes, pin, run}, closure: {kit, version, archive, sources, implementation, retained, records}, scope, instructions: [{playbook, address, text, digest?, source: "position"|"playbook"}], references: [{identity, digest, when: "always"|"seat"|"role"|"as-needed"}], role: {profile, brief}, requestedOperations, effectiveOperations: {status: "host-determined", runner}, missing: [{kind, message, ...}], evidence: {required, states}, kitUpdateAvailable, envelope, digest }`. The digest is sha256 over the sorted-key JSON of `{closure, scope, instructions, references, role, requestedOperations, evidence, effectiveOperations}`; the runtime envelope is outside it. A capability that composes checks adds `{kind: "enforcement", requirement: "constrained-checks", via: "scripts/check.mjs"}` to `missing`: equal content never implies equal permissions. `evidence.required` holds the checks the capability composes; `effectiveOperations.runner` every check the kit's `checks.json` declares. A `when: "role"` reference is the bound profile's own mandate. `instructions` are the isolated method position's cells of the bound playbooks at the scope key, or every cell of them, read by identity, for a whole-procedure activity, a capability the kit's `delivery.json` declares whole, or a position that delivers none of them.

**Scope keys**: `work` activities map to `governance/plan` (task, decision, default), `sequence/plan` (dependencies), `execution/act` (delegation), `context/orient` (progress), `learning/learn` (completion); `delivery` to `context/orient` (understand, diagnose), `governance/plan` (design), `execution/act` (change, default), `learning/learn` (review, deliver); `knowledge` to `context/orient` (find, explain, packet, default), `governance/plan` (place), `learning/learn` (reconcile), `execution/act` (maintain). `--shape` and `--phase` override. A capability its kit's `delivery.json` declares whole carries every cell of its playbooks, read by identity in phase order; any activity whose position delivers no cell of the bound playbooks gets them the same way.

**Retained methods:** the legacy format-3 task pin retains kit/core bytes separately from consumer position. The opt-in complete method contract uses format-4 pins and packet/2, exact runtime attestation, admitted native ownership/composition, retained source/assets/helper bytes and reviewed runner profiles. Missing or changed content refuses without falling back to the current plugin. In an adopted repository the consumer position supplies the packet's laws and seat mandates. A composed check the kit's `checks.json` gives no runner is IA-evaluated when its record runs a built-in evaluator other than `COMP-CHECK` (such as `COMP-COVERAGE`): `ia validate` gives its verdict, it stays in `evidence.required` and `missing` names it (`kind: "ia-evaluated"`). A composed `COMP-CHECK` without a runner is host-run: it stays in `evidence.required` and `missing` reports it (`kind: "check-unavailable"`); a capability none of whose `COMP-CHECK` checks has a runner refuses (`IA-CORE-CHECK-UNAVAILABLE`). The catalogue's validator refuses a host-run check that is not on its maintainer list (`HOST_RUN_CHECKS` in `tools/validate.py`). The KB checks and the authoring field-lint have explicit executor profiles; arbitrary Node imports and ambient executors remain unsupported. A result is execution evidence, not a qualified receipt or host authorization.

## Install and test

```sh
claude plugin install ia@inventarch
codex plugin add ia@inventarch
node --test "tests/*.test.mjs"
```

Node 22. The tests build their kits and a stand-in CLI at runtime and touch no network; `IA_CORE_TEST_CLI=<@inventarch/cli 3.6.0 dist/main.js>` enables the real-CLI cases the kits add.

### Task locator manifests

A check may declare `"arguments": {"manifest": "workspace-file"}` and place `${ARG:manifest}` in one whole argv slot after its executable. `check.mjs --manifest <relative-path>` fills it with a validated regular file inside the workspace. It rejects traversal, absolute paths, links, missing files, duplicate options and arguments that the selected check does not declare. It never adds arbitrary flags or runs a shell. This first argument type serves `ia-kb` 0.3.0's `kb-check-task-locators`; task slugs, base revisions, design roots and checkout mappings remain follow-up work. Path validation is an input boundary, not a sandbox against concurrent filesystem mutation.

### Delivery migration

The reconciled core uses `delivery` only. Rename `development.<activity>`, `development.*` and `defaults.development` bindings to their Delivery equivalents after updating every host. Existing task pins require an explicit `--rebind` for each migrated activity; this writes a new revision and preserves the old revision as history. Review the selected kit and capability before rebinding.

## Supervised service composition

Internal callers of `runMethodCheck` may select `processGroup: "inherited"` only when the calling process is the leader of a supervisor-owned POSIX group; on POSIX the call refuses otherwise. Ordinary calls keep isolated groups. This internal option is not an evaluator argument or an environment switch. An inherited evaluator shares the outer lifetime: its abort kills the caller's whole group, including the caller. Isolated groups are cleaned after root exit, including abrupt exit; when that cleanup kills a live descendant, the result sets `descendantsTerminated` and the descendant's later output is not captured; process and pipe errors terminate descendants before refusal. Windows retains the pinned taskkill tree supervisor, runs no root-exit cleanup and reports `descendantsTerminated: false`; complete service crash containment additionally requires a separately qualified kill-on-close Job Object launcher. These process observations confer no native, ledger or receipt qualification.
