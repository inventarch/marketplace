# ia: set up IA here

The person invoked this as `ia:init`. It is also the protocol the three lanes (`ia:work`, `ia:knowledge`, `ia:delivery`) refer to.

## 0. Initialize, once

1. Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/ia.mjs" doctor --json --host claude` and read its `session` field. If this directory is already a workspace, say so and go to section 2. If the session context reports that the person declined initialization here, today or forever, do not offer it: continue with their request, and initialize only if they ask in this conversation.
2. Ask one question with three choices: initialize now; not today; never for this repository.
3. Initialize now: run `ia.mjs init "<repository root>" --host claude` and show the plan, where `<repository root>` is the absolute path of this project, not the shell's current folder. Only after the person confirms it, run `ia.mjs init "<repository root>" --apply --yes --host claude`. Then offer the default kits: `node "${CLAUDE_PLUGIN_ROOT}/scripts/kit.mjs" bind inventarch/ia-method-kit --install`, `inventarch/ia-kb-kit` and `inventarch/ia-authoring-kit` (each previews; `--install --apply` once the person agrees: it runs `ia install --package @inventarch/public-kits@<version> --apply --yes`, which installs the three kits at once and needs npm and the registry, then writes the keys). If the InventArch connector's tools are available, continue with section 6.
4. Not today: `ia.mjs init "<repository root>" --decline today --host claude`, then continue without offering again. Never: `ia.mjs init "<repository root>" --decline forever --host claude`, and never offer again.
5. Never search the drive, parent directories or other repositories for `.ia` trees or IA tooling. If the IA CLI is missing, say so and name the install (`npm install --save-dev --save-exact @inventarch/cli@3.5.0`, or `IA_CLI_PATH`). `ia:doctor` explains what is not ok.


This plugin, `ia`, carries no method. It carries three lanes, the entry skills `ia:work`, `ia:knowledge` and `ia:delivery` (`delivery` took `development`'s place), a resolver that reads which method kit the repository binds for an activity and delivers it as one packet, kits of IA records under `${CLAUDE_PLUGIN_ROOT}/config/kits/` (the public defaults `ia-method`, `ia-kb` and `ia-authoring`) and in `<IA home>/kits/<kit>/<version>/`, three role briefs, an optional operator-bound hosted UX, UI, design-system and brand service stage reached through Delivery, and a read-only session bootstrap that also offers an InventArch account once per session names a governed repository where no installed kit declares governance handlers, and re-injects the current task pin after a compaction. It ships two MCP servers: the InventArch account connector `inventarch` (remote, OAuth run by the host, section 6), and the IA door as its MCP server `ia` (`node scripts/door.mjs`, which starts `npx -y @inventarch/mcp-door@3.5.0`, never through a shell (on Windows it runs npm's `npx-cli.js` with `node`), told where the bundled kits are), whose `ia_session`, `ia_catalogue` and `ia_method` tools the lanes call, and runs the session, prompt, tool and stop handlers installed kits declare (`handlers.json`). For native method work, everything an agent is told to do comes from the packet, which comes from records read through the IA CLI. Never restate a method from memory.

Scripts run as `node "${CLAUDE_PLUGIN_ROOT}/scripts/<name>.mjs"`; every one prints one JSON value and exits 0 (done), 1 (a refusal, `{ "error": { "code", "message", "candidates"? } }`) or 2 (usage). IA itself runs through `scripts/ia.mjs`: `IA_CLI_PATH` when set, else the repository's pinned `@inventarch/cli`, else exactly 3.5.0 through npx; never an `ia` on PATH.

## 1. What runs without configuration

| Situation | What happens |
| --- | --- |
| No `.ia/src` at or above the folder | The bootstrap is silent; `resolve.mjs` refuses `IA-CORE-NO-WORKSPACE`. Say that the folder is not an IA workspace; `ia init` is the person's to run. A capability its kit resolves outside a workspace (the kit's `unbound` list in `kit.mjs list`; any capability of a kit that lists none) still resolves with `--kit` and `--capability`; the lanes (section 5) still apply. |
| A workspace with no `.ia/bindings.json` | `resolve.mjs` refuses `IA-CORE-NO-METHOD`. Say what is unconfigured: run `kit.mjs list` to show the kits available, and offer `kit.mjs bind <kit> --install` (installs the kit when the lock does not, then writes the keys it recommends) or `kit.mjs bind <kit> --key <entry>.<activity> --capability <capability>`, each previewed, then `--apply` (with `--install` when the kit is not installed) once the person agrees (section 2). The public defaults bind with `kit.mjs bind inventarch/ia-method-kit --install --apply`, `inventarch/ia-kb-kit` and `inventarch/ia-authoring-kit`. A bind to a kit the lock does not install, without `--install`, is refused as `IA-CORE-KIT-NOT-INSTALLED`. Do not invent a method. |
| A bound activity | The packet arrives (section 3). The method is read from a restored copy of the kit in a per-user temp folder. When the kit is installed (`.ia/distributions.lock.json`), the laws and seat mandates come from the repository's position at `--seat`; otherwise they are the kit's own and `--seat` sets only `scope.seat`. |

## 2. Setup and diagnostics

- `kit.mjs list`: every kit the core can resolve (this plugin's, then those installed in `<IA home>/kits/`): its origin, latest release and versions, checks, whole capabilities, the keys it offers, and `unbound` (the capabilities it resolves outside a workspace, `null` for any). `kit.mjs check [<kit>]`: each kit's latest release agrees with its sources, records and sidecars. `kit.mjs status <kit> [<repo>]`: installed or not, current or not. `kit.mjs root <kit>`: a folder to pass as `--root` to `ia.mjs position` and `ia.mjs read` when reading a kit's records directly.
- Every write below previews unless `--apply`; show the preview and apply only when the person agrees. `kit.mjs add <kit> [<repo>]`: installs the kit's latest release into the workspace (it writes `vendor/ia/` and `.ia/distributions.lock.json`; on an older language base it also moves the other installed core kits, listed as `upgraded` and `requests`). `kit.mjs add --from <folder|archive>`: validates a kit and installs it into `<IA home>/kits/<kit>/<version>/`; an installed version is never overwritten. `kit.mjs bind <kit> [<repo>] [--install]`: the keys the kit recommends, each new, already bound so, or kept because the repository binds it otherwise; only new keys are written. It refuses a kit the lock does not install (`IA-CORE-KIT-NOT-INSTALLED`, on a preview too, with a key as without). `--install` installs it first: for a kit the public-kits package carries, `ia install --package @inventarch/public-kits@<version> --apply --yes` (the version is in `config/public-kits.json`; it installs every kit the package carries, seeds a language-only lock and restores it when the workspace has none, and needs npm and the registry); for any other kit, the same as `add`. `IA-CORE-INSTALL-CONFLICT` means the lock already installs a carried kit as a direct package row: install the kit the direct way instead, with `kit.mjs add <id> --apply`, then bind it; `kit.mjs upgrade` does not clear the conflict. `IA-CORE-INSTALL-UNCERTAIN` means the install may have committed: inspect the lock, never retry blindly. `kit.mjs upgrade [<kit>] [<repo>]`: installed kits behind their latest release, adopted with `--apply`. `kit.mjs repin --project <p> --task <t>`: the task pin's keys whose kit moved, rebound one by one with `--apply`. `kit.mjs rebind <from-kit> <to-kit> [--keys a,b]`: moves bound keys to another kit that has the same capabilities, for a renamed or split kit.
- `bind.mjs show [<repo>]`, `bind.mjs set <entry>.<activity> <kit> <capability> [<repo>] [--add]`, `bind.mjs default <entry> <kit> <capability>`, `bind.mjs precedence <kit...>`: the repository's `.ia/bindings.json`. A key is `<entry>.<activity>`; `<entry>.*` answers the entry's other activities; `defaults.<entry>` answers last. Several candidates for one key need `precedence` (first kit wins), else the resolve refuses `IA-CORE-CONFLICT` and lists them: ask the person which, never pick.
- The on-write hook (PostToolUse after Write, Edit or MultiEdit; Claude Code only) runs the checks a carried kit declares for the file just written, such as a per-card design check, and hands back their report; it never blocks and is silent for other files.
- The bootstrap (SessionStart) has already said, inside a workspace, the workspace identity and revision, the installed kits and the bound keys. When it did not run (Codex, a sandbox), run `bootstrap.mjs` with `{"cwd": "<root>"}` on stdin, or go straight to a resolve.

## 3. The delivery protocol

For UX improvements, atomic UI components, brand voice and palette, design-system typography, tokens or accessibility audits, Delivery checks the optional operator binding through `${CLAUDE_PLUGIN_ROOT}/references/design-stage.md`. Only an explicitly selected, authorized and available service uses hosted execution. Otherwise continue with the native protocol below, reporting unavailable capabilities without inventing a method. Software and IA architecture always retain native resolution.

1. **Resolve before acting.** `node "${CLAUDE_PLUGIN_ROOT}/scripts/resolve.mjs" --entry <work|delivery|knowledge> --activity <activity> [--subject <what>] [--seat <identity>] --json`. Add `--project <p> --task <t> [--run <r>]` when the work is a coordination task (the resolve is then pinned to the task under `<IA home>/work-v1/<project>/<task>/binding.json`, the IA home being an absolute `IA_HOME`, else `~/.ia`, one entry per activity key: a key's first resolve adds it, later ones keep its kit version and capability; two runs of one task share it). Outside an IA workspace, a capability its kit resolves there (the kit's `unbound` list in `kit.mjs list`; any capability of a kit that lists none; otherwise `IA-CORE-UNBOUND-UNDECLARED`) resolves with `--kit <kit> --capability <name> [--profile <name>]` instead of a binding; nothing is pinned. The activity picks the scope key (`--shape`/`--phase` override): `work` task and decision go to governance/plan, dependencies to sequence/plan, delegation to execution/act, progress to context/orient, completion to learning/learn; `delivery` understand and diagnose to context/orient, design to governance/plan, change (default) to execution/act, review and deliver to learning/learn; `knowledge` find, explain and packet (default) to context/orient, place to governance/plan, reconcile to learning/learn, maintain to execution/act. A capability its kit declares whole (each lane entry, such as `method-operate`, `kb-knowledge` and `authoring-deliver`) arrives with every cell, orient, plan, act and learn in order; `--phase` selects one cell of any other.
2. **Read the packet.** `binding` (key, kit, capability, `revision` of the task pin, `rebound`); `closure` (the kit version and the records the packet rests on); `scope` (the key, seat and workspace revision); `instructions` (the playbook cells: do what they say, in order, and nothing a cell does not say); `references` (`when: always` are rules to honour throughout; `seat` are the mandates of the seat; `role` is the role's own mandate, the moves it runs under; `as-needed` are records to read with `ia.mjs read <identity>` when a step needs them); `role` (the brief you take on; it grants no authority); `requestedOperations` (the effects the capability asks for) against `effectiveOperations` (`host-determined`: what the host actually permits is decided by its tools and the person, not by the packet); `missing` (each entry has a `kind`: `enforcement` means the capability requires a restriction this host does not enforce and names how to honour it by hand; `kit-update`, `seat`, `record`, `instructions`, `role`, `checks`, `note`); `evidence` (the checks the capability requires, and the states a claim moves through: proposed, attempted, executed, verified, accepted); `kitUpdateAvailable` (say so, keep the pin, offer `--rebind`); `digest` (cite it).
3. **Follow only the packet.** No method from memory, no step the cells do not give, no record the closure does not name unless a reference points there. When the packet lacks something, say what is missing rather than fill it in.
4. **Cite sources.** A record by identity and digest, a file by path and line, a command by its exact text and exit code, the packet by its digest. A claim without a source is proposed, not verified.
5. **Stop on conflict.** A refusal with candidates, an instruction that contradicts a rule in `references`, a brief that asks for more than the host or the person allows: stop and ask. Never resolve a conflict by choosing.
6. **Proposed versus verified.** Every result carries its evidence state. `verified` needs the output of a run check (`check.mjs`, section 4) or of a command you ran; `accepted` is the person's word. Never promote a state yourself.
7. **A brief grants no authority.** `role.brief` says what to do, not what you may touch. The workspace's mandates, the host's tools and the person decide that; report requested against effective operations.

Refusals and what to do: `IA-CORE-NO-WORKSPACE` and `IA-CORE-NO-METHOD` as in section 1; `IA-CORE-CONFLICT` ask; `IA-CORE-KIT-NOT-INSTALLED` the lock does not install the kit, offer the install command the refusal names; `IA-CORE-KIT-UNKNOWN` the binding names a kit this plugin does not carry, say so; `IA-CORE-RUN-MISMATCH` the task folder belongs to another repository, use another; `IA-CORE-REBIND-REQUIRED` the binding of a key the task pinned changed, ask before passing `--rebind` (it moves that key and its kit's version, not the others); `IA-CORE-UNBOUND-IN-WORKSPACE` `--kit` was given inside an IA workspace, bind the kit there instead; `IA-CORE-POSITION` run the command the message names; `IA-CORE-CLI-MISSING` set `IA_CLI_PATH` or install `@inventarch/cli` 3.5.0 in the repository (an install that is not that package, or lacks its entry, is refused too); `IA-CORE-CLI-UNSUPPORTED` the repository's CLI does not ship the language base the kit release locks (an older major, or within a major a CLI without the kit's base), so it cannot restore the kit: say so, and pin `@inventarch/cli` 3.5.0 or set `IA_CLI_PATH`.

## 4. Agents and checks

- `reader` (read-only): evidence from the repository, its records and the kit. `worker`: a bounded change within the packet's scope. `checker`: runs checks and reports them. Give each the packet (or its path), the repository root and `${CLAUDE_PLUGIN_ROOT}`; each takes its role from `role.brief` and reports requested against effective operations.
- The `reader` and `worker` list the IA door's tools (`mcp__ia-workspace`), which exist only once `ia host` has registered the door for the workspace; without the door they use the CLI.
- Checks run only through `node "${CLAUDE_PLUGIN_ROOT}/scripts/check.mjs" <check-name> [--root <repo>]`: it runs a `@check` the bound or pinned kit declares, with the argv the kit fixed, and refuses anything else (`IA-CORE-CHECK-UNKNOWN`). That script is the restriction; the `checker` brief runs nothing else. A check that exits 0 is `verified` evidence; any other exit is a finding, never a pass.

## 5. Route to the lanes that do the work

Hosted UX, UI, design-system and brand requests check `${CLAUDE_PLUGIN_ROOT}/references/design-stage.md` through Delivery; missing binding or unavailable runtime falls back to native resolution. This service route requires an explicit API origin, an existing OAuth service token with client registration and admission, and a separately configured runtime/provider. Its workspace adoption and runs are explicit; it never approves effects.

| The work is | Then |
| --- | --- |
| a governed task (a repository with `.ia/governance.json`) | it needs a kit that declares governance handlers, the `ia-governance` kit (`ia kit add`, with an account); until one is installed, say so before changing anything and never treat the repository as ungoverned |
| designing new IA words, systems, workspaces or kits | outside the public kits: by hand from the public IA documentation, or the subscription methods an InventArch account serves |
| meetings, design probes and audits, organisation-wide knowledge custody and other subscription methods | kits served once the person has signed in to InventArch through the bundled connector (`/mcp`, or `claude mcp login inventarch`); section 6 installs and binds them |

When a lane is not available, say so and continue with the packet alone.

## 6. After the person signs in to InventArch

The core bundles the InventArch account connector, the MCP server `inventarch` (`https://api.inventarch.dev/mcp`). The person signs in through `/mcp` (or `claude mcp login inventarch`); the host runs the OAuth sign-in and keeps the token. This plugin ships no secret and stores no token, and neither does this protocol: never write a token, a sign-in code or a signed URL into a file, a record, a log or your reply. When the connector's tools are not available in this session (Claude Code names them `mcp__plugin_ia_inventarch__kit_offerings` and `mcp__plugin_ia_inventarch__kit_download`), the person has not signed in or the host is not Claude Code: say so, name the sign-in, and stop here. Nothing else in this skill needs the account.

When they are available, set up everything from that authorization, in this order:

1. **List what the account offers.** Call `kit_offerings`. Each offering names a kit id and a release version, and its access, `public` or `licensed`. The public kits are already bundled; take the `licensed` ones. Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/kit.mjs" list` and drop every offering whose kit and version are already installed (an installed version is never overwritten). Show the person what is left, and install nothing until they agree.
2. **Download and verify each one.** Call `kit_download` with `{ "id": "<kit id>", "version": "<version>" }`. It returns `{ url, expiresAt, archive }`: a 10-minute signed URL, and the SHA-256 the bytes behind it must hash to. Pipe that, with the kit id and version, to the fetch script on stdin, so the URL never reaches a command line or a file: `{"id":"<kit id>","version":"<version>","url":"<url>","archive":"<archive>"}` into `node "${CLAUDE_PLUGIN_ROOT}/scripts/kit-fetch.mjs" get`. It downloads over https, writes the archive only when its SHA-256 equals `archive`, and prints `{ "file", "sha256", "bytes" }`. A digest mismatch or an expired URL is a refusal: report it verbatim, do not retry with a guessed URL, and call `kit_download` again for a fresh one only if the person asks.
3. **Install it.** `node "${CLAUDE_PLUGIN_ROOT}/scripts/kit.mjs" add --from "<file>"` previews and validates (the kit must be an installable release, or `add --from` refuses it); show the preview, and run it again with `--apply` once the person agrees. Then remove the download: `node "${CLAUDE_PLUGIN_ROOT}/scripts/kit-fetch.mjs" clean "<file>"`, whatever the outcome. If `add --from` refuses the archive, say what it says and carry on with the next kit.
4. **Bind as the kit recommends.** Inside an IA workspace, `kit.mjs bind <kit id> --install` previews the install and the keys the kit recommends; `--install --apply` once the person agrees (section 2), which also installs a kit added with `add --from` that the lock does not yet install. Outside a workspace, offer section 0 first. Several kits claiming one key is `IA-CORE-CONFLICT`: ask which wins, never choose.
5. **Report.** Per kit: offered, downloaded and verified (the SHA-256), installed or refused (with the reason), bound keys. Name anything skipped. Do not repeat the URL, the expiry or any token.
