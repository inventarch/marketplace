# Screening specification review

InventArch, 2026-11-06, issue 22. Commit d738f64 retains the spec and 30 observed failing missing-tool tests before implementation. Independent architecture/security and test-adequacy reviews, plus an internal adversarial review, found preimplementation gaps. No implemented security behavior was claimed at that stage.

Corrections before implementation: require the actual publicRoot explicitly; reject multiply linked input documents; exercise resolved checkout aliases; isolate equal-length hash drift and actual JSON media-type changes; require path/media reason codes; define result classification and evaluation precedence; bound entries, values, directories and nesting; constrain API/CLI error disclosure; retain resource-limit, manifest-pin, malformed-input, empty-directory and CLI controls. Three independent verifiers confirmed the custody/default-root and aliased-input risks. The strengthened suite has 48 observed failures before the tool exists, zero skips.

The lexical profile explicitly excludes markup rendering, character references, soft-line joining and arbitrary code/encoding interpretation. Synthetic controls demonstrate those limits rather than implying decoded semantic coverage. Exact-payload semantic review is mandatory in addition to a lexical pass. Registry completeness and acceptance remain external operator responsibilities; selected hashes cannot certify either. The private registry proposal must be independently classified and accepted before it can authorize publication screening.

This is a repository maintainer implementation, not a shipped kit evaluator or a replacement for the shared conformance checker. Direct pack integration and publication enforcement remain subsequent work. No tool is being given permission to publish, access private services or execute a candidate.

Implementation review found incorrect status classification for changing input documents, omitted Windows-invalid filename characters, a CLI entry check that silently skipped execution through a linked directory, and manifest row validation that could apply path policy before discovering a malformed later row. Independent reviewers confirmed the changing-input and filename cases, and separately reproduced the linked-directory exit-zero bypass. Regression commits 05b7f9a and 28b528e precede fixes: the latter records 65 tests, 52 passing and 13 failing, with zero skips. The failures isolate ten filename controls, changing-input classification, linked CLI execution and mixed manifest shape/path precedence.

Additional controls cover entry and directory bounds, deep JSON, a multi-megabyte JSON string, the findings cap and unknown CLI arguments. Resource-limit results remain not-evaluated. Review clarified the findings cap and the trusted frozen-snapshot assumption; the lexical normalization is not a claim of complete filesystem Unicode folding or concurrent-writer isolation. Large JSON tokens currently pass the regression; replacing the recursive regular-expression matching strategy with an iterative scanner avoids reliance on its stack behavior.

The next internal review accepted those corrections but identified an import-time exception when the host's argv does not name a file and a malformed-row type classification gap. Independent verification reproduced the stdin import error. Commits 950560a and d375cf1 retain the new controls before fixes: the full 68-test suite reports 66 passes and two failures. The API must import without invoking the CLI from stdin/eval, while direct linked invocation must still produce screening evidence. Row types are shape constraints; their failures are not-evaluated. Root alias behavior is now explicit. Follow-up hardening should use descriptor-bound bounded reads and exact bigint identities, qualify high-token-count performance and expand supported publication formats before kit-pack integration. Those are outside this controlled frozen-text profile, not grounds to claim hostile-filesystem isolation today. Independent large-token probes did not reproduce the earlier speculative regex-stack failure.

The subsequent review found no blocker but identified a Low directory-prefix portability defect: distinct leaf keys can still share a conflicting file/directory prefix or inconsistently cased directory. Commit ae5a932 retains its observed failing policy control. Independent review confirmed the defect and required reversed-order cases plus a clean shared-directory sibling control before correction. Prefix-map validation must preserve those valid siblings. The speculative performance/race concerns remain issue 23 follow-ups rather than established failures within the frozen-input model.
