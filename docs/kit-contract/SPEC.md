# Public kit contract expectation baseline

Task and spec: `kit-contract-public-baseline`; plan: `kit-contract-qualification`; [issue 21](https://github.com/inventarch/marketplace/issues/21). Authoring attribution: InventArch.

The baseline supplies proposed public expectations before a native contract or checker is implemented. It consists of `expectations.json` and `context.md`, reviewed together. `review.md` and `verification.md` retain development evidence and are not normative baseline inputs. The separately owned `SCREENING-SPEC.md`, `screening-review.md` and `screening-verification.md` describe the publisher tool and also are not normative baseline inputs. The baseline is not shipped in the plugin or any kit. Version 0.1.0 is a proposal, not a published contract release. All behavioral evaluators remain unavailable.

The four contracts must retain 14 requirements and 163 individually attributed cases: candidate conformance (8/86), qualification inputs (2/34), programme audit (1/6) and checker execution (3/37). Preserve every stable contract/requirement/case identity, association, kind, given, request, expected outcome and grammar reference. A repeated semantic variant under another requirement remains a separate obligation. The complete normative context accompanies the data, including applicability, trusted assessment selection, payload identity, oracle independence, bootstrap, consumer verification, current eligibility and custody.

The repository test reads these artifacts as inert data using strict UTF-8 decoding with BOM preserved. Approval identifies the two complete text SHA-256 pins: expectations JSON and normative context, normalizing CRLF to LF only. The exact JSON text pin detects duplicate object keys whose earlier values a JSON parser would discard. Invalid UTF-8 refuses before hashing. Missing data, duplicate or reassigned cases, changed context or expectations, incomplete requirement information and fabricated evaluator standing must fail. Pins are constants in the test, never recalculated from the candidate at runtime. No automatic snapshot-update command is provided.

A supplementary semantic SHA-256 pin covers the parsed JSON value. Its algorithm is precisely ECMAScript JSON.stringify with a replacer that rebuilds each non-array object from Object.keys sorted with the default UTF-16 code-unit comparator. Array order is preserved; integer-index keys retain ECMAScript enumeration ordering; string escaping and number formatting are those of JSON.stringify. Hash its UTF-8 result without Unicode normalization. This semantic pin aids review but does not replace the two exact-text approval pins.

Negative controls mutate copies only. Each first verifies the unchanged baseline, then demonstrates rejection of a specific loss or drift, including changes preserving all counts. Context controls cover edits, section omission and trailing-newline loss, while CRLF-only representation changes remain valid. Structural controls exercise duplicate IDs, missing owner/intent, unknown case kinds and fabricated evaluator standing independently of the pins. Optional grammar metadata must retain its original presence and value; required associations are also expressed in case identity and given text, so absence of an optional field cannot erase a case. These tests establish baseline integrity, not execution of the 163 scenarios. They establish neither safe-publication screening, independent approval authenticity, native admission, runtime conformance, final-artifact verification, checker eligibility nor release authority. They are repository tests, not shipped checker code.

Independent review must compare the proposed public semantics against the governing intent before the baseline is frozen for lowering. Any changed expectation requires an explicitly reviewed versioned delta; changing the data and its test pin together is not approval. First adoption also requires public review/approval evidence tied to the exact public content digests. Private source provenance is not a required public qualification input.

Exposing a proposed branch for public review requires authorized publisher screening of its complete new payload and history against the operator-maintained private-identity list held outside this repository. A missing list is not evaluated, never a pass. This includes test, review, provenance and newly authored PR metadata; sensitive screening inputs remain private. Exact screened-head, manifest-digest and safe result attestations are retained in [PR24's conversation](https://github.com/inventarch/marketplace/pull/24), separately from historical development tests. Exposure for review does not adopt or freeze the baseline, authorize merge or release, or screen later lowered/generated artifacts. Local integrity tests and generic-label review cannot substitute for this obligation.

Exact public catalogue exports, native representation, executable checker ownership/profile/binding, behavioral fixtures and approvals, first-checker bootstrap, eligibility channel and both publication consumers remain subsequent qualification work. Passing this slice does not close those tasks or permit new kit cuts. No merge or release is part of this task.
