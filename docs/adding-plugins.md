# Add or change a plugin or a kit

1. **Need and owner.** Establish the need, the audience and a distinct trigger. Most additions belong as a public system + starter kit (a method the core resolves on top of the open Engine) or a stage skill inside the core, not as a new plugin. Vocabulary (`@system` and `@schema`) and methodology (kits) are separate layers: Engine lowering changes belong in `inventarch/ia`, proprietary kit bodies execute on the InventArch API rather than shipping here, and code tied to a private API, custom MCP server or organisation authentication stays in its owner's private repository or catalogue (`public-systems-and-kits-custody`).
2. **Plugin layout.** `plugins/<name>/.claude-plugin/plugin.json`, `.codex-plugin/plugin.json`, `CODEX.md`, `README.md`, `CHANGELOG.md` and `skills/<name>/SKILL.md` (the router, named after the plugin). Every skill opens with the Codex bridge line, `**Codex:** read [the Codex host instructions](../../CODEX.md) first.` Stage skills, `references/`, `templates/`, `examples/`, `agents/`, `config/` and node `scripts/` are allowed; hooks, `.mcp.json`, commands, settings and `bin/` are not (decision `public-plugin-components`), apart from the core's two pinned hooks (`public-core-hooks`).
3. **Manifests.** The Codex manifest is the Claude manifest without `displayName` and `dependencies`, plus `skills` and the `interface` block (`public-codex-manifest-interface`). Every manifest says `"license": "Apache-2.0"` (`public-apache-license`). Catalog entries carry no version.
4. **Kits.** A kit is authored under `kits/ia-<name>` (`public-kit-naming`), never inside a plugin; `kits/bundle.json` maps it into the plugin that carries it. See [the kit README](../kits/README.md) for the release workflow.
5. **Selection.** `python tools/selection.py` proposes `export-selection.json` from the shipping rule (both catalogs and every plugin file outside `tests/`); review the diff, then `--write`.
6. **Release note.** Every change that ships adds a release note naming the plugin (`node tools/release.mjs note`, decision `public-release-notes`); `python tools/consistency.py --base origin/main` enforces it. The release pull request, not yours, bumps the version in both manifests and `sources.lock.json` `pluginVersion` and writes the `CHANGELOG.md` entry ([releases/README.md](../releases/README.md)). A new plugin starts at its first version and its first `CHANGELOG.md` entry.
7. **Gates.** Run every gate in [AGENTS.md](../AGENTS.md#gates) before committing.

The tools under `tools/`, the schemas under `schemas/` and the tests under `tests/` hold these rules: `validate.py` (what ships), `consistency.py` (hygiene, pins, versions, release notes, published releases), `release.mjs` (release notes and the release pull request), `selection.py`, `bundle-kits.mjs`, `kit.mjs` (the maintainer verbs), `pack-kit.mjs`, `check-language.mjs`, `run-native-tests.mjs`, `smoke-codex.mjs` and `package.py`.
